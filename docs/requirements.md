# Требования к сервису выполнения заданий

## 1. Сценарии использования

### Сценарий 1. Выполнение вычислительной задачи

**Цель:** выполнить математическую операцию и получить результат.

**Участник:** клиент API.

**Основной поток:**
1. Клиент отправляет запрос на создание задачи, указывая операцию и параметры.
2. Система создаёт Job и возвращает его идентификатор.
3. Диспетчер выбирает вычислительный обработчик.
4. Обработчик выполняет операцию.
5. Система сохраняет результат и переводит задачу в состояние `done`.
6. Клиент запрашивает результат по идентификатору задачи.

**Критерий приёмки:**
- **Дано:** доступна операция сложения.
- **Когда:** клиент создаёт задачу сложения чисел 15 и 25.
- **Тогда:** задача успешно выполняется, её состояние становится `done`, а результат равен 40.

### Сценарий 2. Обработка текста

**Цель:** выполнить преобразование текста.

**Участник:** клиент API.

**Основной поток:**
1. Клиент отправляет текст и указывает операцию преобразования в верхний регистр.
2. Система создаёт Job.
3. Диспетчер выбирает текстовый обработчик.
4. Обработчик преобразует текст.
5. Система сохраняет результат и завершает задачу.

**Критерий приёмки:**
- **Дано:** доступен обработчик преобразования текста.
- **Когда:** клиент отправляет текст `hello`.
- **Тогда:** задача завершается со статусом `done` и результатом `HELLO`.

### Сценарий 3. Получение состояния и результата задачи

**Цель:** узнать текущее состояние задачи и получить результат выполнения.

**Участник:** клиент API.

**Основной поток:**
1. Клиент создаёт задачу и получает её идентификатор.
2. Клиент отправляет запрос на получение информации о задаче.
3. Система находит задачу в хранилище.
4. Система возвращает её состояние и доступный результат.

**Критерий приёмки:**
- **Дано:** в системе существует задача с известным идентификатором.
- **Когда:** клиент запрашивает информацию по этому идентификатору.
- **Тогда:** система возвращает текущее состояние задачи и результат, если выполнение завершено.

### Сценарий 4. Неизвестная операция (ошибочный)

**Цель:** предотвратить выполнение неподдерживаемой операции.

**Участник:** клиент API.

**Основной поток:**
1. Клиент отправляет запрос с неизвестным типом операции.
2. Система проверяет наличие обработчика в Registry.
3. Подходящий обработчик не найден.
4. Система отклоняет запрос и возвращает сообщение об ошибке.

**Критерий приёмки:**
- **Дано:** запрошенная операция отсутствует в Registry.
- **Когда:** клиент пытается создать такую задачу.
- **Тогда:** система возвращает ошибку `400` с понятным описанием и не создаёт Job.

### Сценарий 5. Некорректные параметры (ошибочный)

**Цель:** исключить выполнение задач с неверными входными данными.

**Участник:** клиент API.

**Основной поток:**
1. Клиент отправляет запрос с некорректными параметрами.
2. Система проверяет формат и типы входных данных.
3. Проверка обнаруживает ошибку.
4. Система отклоняет запрос и сообщает причину.

**Критерий приёмки:**
- **Дано:** операция сложения принимает числовые параметры.
- **Когда:** клиент передаёт число 15 и строку `abc`.
- **Тогда:** система возвращает ошибку `400` с описанием некорректного параметра и не создаёт Job.

### Сценарий 6. Недоступность внешнего сервиса (ошибочный)

**Цель:** корректно обрабатывать сбои внешней HTTP-зависимости.

**Участник:** клиент API.

**Основной поток:**
1. Клиент создаёт задачу, требующую обращения к внешнему HTTP-сервису.
2. Система создаёт Job и начинает выполнение.
3. Обработчик отправляет HTTP-запрос.
4. Внешний сервис не отвечает в пределах установленного времени.
5. После ограниченного числа повторных попыток система прекращает выполнение.
6. Задача переходит в состояние `failed`, информация об ошибке сохраняется.

**Критерий приёмки:**
- **Дано:** внешний HTTP-сервис недоступен.
- **Когда:** выполняется задача, использующая этот сервис.
- **Тогда:** система не ожидает ответ бесконечно, завершает ограниченные повторные попытки и сохраняет задачу со статусом `failed` и описанием ошибки.

## 2. Жизненный цикл Job

Каждая принятая к выполнению задача представлена объектом Job с уникальным идентификатором.

**Состояния:**
- `created` — задача создана и ожидает выполнения.
- `running` — задача выполняется.
- `done` — задача успешно завершена.
- `failed` — выполнение завершилось ошибкой.

**Разрешённые переходы:**
- `created → running`
- `running → done`
- `running → failed`

**Запрещённые переходы:**
- `done → running`
- `failed → running`
- `done → failed`
- `created → done`

После перехода в `done` или `failed` задача считается завершённой. Недопустимые переходы должны отклоняться системой.

Ошибки валидации при создании задачи обрабатываются до создания Job. Ошибки, возникающие во время выполнения, переводят существующую задачу в `failed`.

## 3. Что предложил ИИ

**Промпт:**

> Проанализируй основной сценарий создания и выполнения задачи (Job) в сервисе с API, диспетчером и обработчиками. Предложи три дополнительных способа, которыми этот сценарий может завершиться ошибкой или привести к некорректному поведению системы. Для каждого случая объясни причину и возможный способ обработки.

### Предложение 1. Повторная отправка одного запроса

**Предложение ИИ:** из-за сетевой ошибки клиент может повторно отправить запрос, что приведёт к созданию двух одинаковых задач.

**Решение:** принято.

**Причина:** повторные запросы не должны создавать дублирующие задачи. Предусмотрим ключ идемпотентности, позволяющий повторно получить уже созданную задачу.

### Предложение 2. Запрос несуществующей задачи

**Предложение ИИ:** клиент может запросить состояние Job по идентификатору, которого нет в системе.

**Решение:** принято.

**Причина:** система должна корректно обрабатывать отсутствие задачи, возвращая ошибку `404`, а не внутреннюю ошибку сервера.

### Предложение 3. Некорректный ответ внешнего сервиса

**Предложение ИИ:** внешний HTTP-сервис может вернуть повреждённые данные или ответ в неожиданном формате.

**Решение:** принято.

**Причина:** даже доступный внешний сервис может возвращать некорректные данные. Необходимо проверять формат ответа, сохранять диагностическую информацию и завершать Job со статусом `failed`, если корректный результат получить невозможно.
