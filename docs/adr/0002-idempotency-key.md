# ADR-0002: Идемпотентное создание Job по Idempotency-Key

- **Дата:** 2026-11-15
- **Статус:** принято для проектируемой архитектуры P2
- **Команда:** Qeu

## Контекст и ограничения

Клиент может случайно повторить `POST /jobs`: двойной клик, сетевой таймаут, потерянный HTTP-ответ или повторная отправка после сбоя. Без защиты сервис может создать несколько Job для одной логической операции. Для внешних HTTP-операций это особенно опасно: повторное создание Job может привести к дублированию обращения к поставщику.

Сервис должен отличать **повтор идентичного запроса** от **повторного использования ключа с другим содержимым**, не усложняя контракт для простого клиента. Текущий OpenAPI допускает запросы без заголовка `Idempotency-Key`.

## Решение

Для `POST /jobs` поддерживается необязательный заголовок `Idempotency-Key` длиной от 1 до 128 символов.

1. До создания Job API проверяет существование операции и корректность параметров.
2. Если ключ указан, `JobService` ищет существующую запись этого ключа и сравнивает **нормализованный запрос** (`operation` и `params`); порядок полей JSON не должен менять результат сравнения.
3. **Новый ключ:** Job и привязка ключа создаются атомарно в постоянном хранилище; API возвращает `202 Accepted` и Job в состоянии `created`.
4. **Тот же ключ и тот же нормализованный запрос:** API возвращает `200 OK` с текущим представлением **прежней** Job и тем же `id`; новая задача не создаётся и прежняя не запускается повторно.
5. **Тот же ключ, но другой запрос:** API возвращает `409 Conflict` с `ApiError.error.code = IDEMPOTENCY_KEY_REUSED` и `field = Idempotency-Key`; существующая Job не изменяется.
6. **Заголовок отсутствует:** каждый корректный `POST` считается отдельным запросом и может создать новую Job.

Ключ уникален в области сервиса Qeu (для текущего прототипа без учётных записей). Защита действует **пока хранится запись о Job и её ключе**; бессрочная дедупликация не обещается. После появления учётных записей область уникальности потребуется пересмотреть.

## Рассмотренные альтернативы

| Вариант | Плюсы | Почему не выбран |
|---|---|---|
| Не защищаться от повтора | Минимальная реализация | Двойной клик и повтор при таймауте создают лишние Job |
| Дедупликация только по телу запроса | Не нужен заголовок | Нельзя отличить намеренное повторное вычисление от ошибочного повтора |
| Обязательный `Idempotency-Key` для всех запросов | Строгое поведение | Лишняя сложность для простых клиентов и учебного прототипа |
| Необязательный ключ с проверкой нормализованного содержимого | Совместим с простыми клиентами, защищает явные повторы | Требует атомарного хранения и сравнения содержимого |

## Цена и последствия

- Необходимы хранилище ключей/отпечатков запроса, ограничение длины и атомарная операция создания записи; простая проверка «сначала найти, потом вставить» недостаточна при гонках.
- Повтор может вернуть `200`, даже если исходная Job уже в `running`, `done` или `failed`; это не новый запуск.
- При отсутствии заголовка возможны дубли, о чём клиент должен знать.
- Удаление старых данных ограничивает срок защиты от повторов; конкретная политика хранения будет определена при реализации БД.
- Эта защита относится к **созданию Job**, а не гарантирует exactly-once внешнее действие. Неопределённый результат вызова внешнего провайдера требует отдельных мер в HTTP-адаптере и политике восстановления Worker (ADR-0001).

## Условия пересмотра

Пересмотреть решение при введении многопользовательской авторизации, фиксированного срока хранения ключей, внешних платных операций с обязательной защитой от дублей или требований гарантировать поведение после долгого простоя системы.

## Проверка решения

- Два параллельных запроса с одинаковым ключом и одинаковыми данными создают одну Job.
- Повтор того же ключа и данных возвращает `200` и прежний `id`.
- Повтор ключа с изменёнными параметрами возвращает `409 IDEMPOTENCY_KEY_REUSED`.
- Отсутствие ключа допускает две независимые Job.
- Некорректные параметры отклоняются до создания Job и не должны резервировать ключ.
