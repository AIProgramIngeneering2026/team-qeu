# ADR-0001: Фоновое выполнение Job

- **Дата:** 2026-11-15
- **Статус:** принято для проектируемой архитектуры P2
- **Команда:** Qeu

## Контекст и ограничения

Сервис принимает вычислительные, текстовые и внешние HTTP-задачи через `POST /jobs`. Продолжительность операции заранее неизвестна: внешний сервис может отвечать медленно или завершиться ошибкой. При этом клиенту требуется стабильный API для создания задачи, проверки состояния и получения результата.

Существующий контракт использует состояния `created`, `running`, `done`, `failed`; переходы в терминальные состояния необратимы. В P2 проектируются интерфейсы и границы компонентов, а реализация предусмотрена последующими практиками. Для первой версии предпочтительна архитектура, которую может поддерживать небольшая команда.

## Решение

Разделить приём запроса и исполнение задачи:

1. `POST /jobs` сначала проверяет `operation`, параметры и при необходимости `Idempotency-Key`.
2. `JobService` атомарно сохраняет новую задачу со статусом `created`. После успешного сохранения API возвращает `202 Accepted` с её идентификатором.
3. Фоновый `Worker` выбирает сохранённые задачи `created`, атомарно переводит выбранную задачу в `running` и вызывает `Dispatcher`.
4. `Dispatcher` находит `Tool` через `Registry`; `Tool` возвращает `ToolResult`.
5. `Worker` сохраняет результат (`done`) либо диагностируемую ошибку (`failed`). `GET /jobs/{id}` не запускает задачу повторно и возвращает актуальное состояние.

Для начальной реализации предполагается **один развёртываемый сервис** с отдельным логическим фоновым исполнителем и постоянным `JobRepository`. Обмен задачами основывается на сохранённом состоянии, а не только на ненадёжной очереди в оперативной памяти. Детали конкурентного доступа должны обеспечить атомарное взятие Job в работу.

## Рассмотренные альтернативы

| Вариант | Плюсы | Почему не выбран |
|---|---|---|
| Синхронное исполнение внутри `POST /jobs` | Простота для коротких вычислений | Долгие HTTP-операции блокируют ответ; сложно отслеживать состояние и повторять запросы |
| Вызов фоновой функции без постоянного хранения Job | Быстрый прототип | После перезапуска теряются незавершённые задания и информация об их состоянии |
| Отдельная распределённая очередь и самостоятельные Worker-сервисы | Масштабирование и независимый запуск | Избыточная инфраструктура и эксплуатационная сложность для первой версии |
| Постоянное хранение Job и фоновый Worker в составе одного сервиса | Простой контракт, восстановимость данных, расширяемость | Требует аккуратной конкурентной обработки и политики восстановления |

## Цена и последствия

- Клиенту нужен второй запрос `GET /jobs/{id}`: результат не обязательно доступен сразу после `POST`.
- Требуются хранение состояний, атомарное взятие задач в работу и тесты переходов.
- HTTP-ответ `202` означает **принятие задачи**, а не успешное выполнение.
- После аварийного завершения задачи в `running` нельзя безусловно запускать повторно: внешний поставщик мог обработать запрос, но ответ потерялся. Нужна отдельная политика восстановления/сверки и ограничения повторов HTTP-адаптера. До её реализации автоматическое восстановление таких задач не обещается.
- Для внешнего вызова используются ограничение времени ожидания, проверка формата ответа и безопасная политика retry. `Tool` не меняет состояние Job самостоятельно.

## Условия пересмотра

Пересмотреть решение, если нагрузка потребует независимого масштабирования обработчиков, появится необходимость гарантированной распределённой доставки, возникнут требования к более строгим срокам исполнения или будет доказано, что выбранное восстановление после сбоев недостаточно надёжно.

## Проверка решения

- Создание валидной задачи возвращает `202` и `Job.status = created`.
- Разрешены только `created → running → done/failed`; обратные переходы запрещены.
- Повторный `GET` не запускает исполнение.
- Тесты проверяют однократное взятие Job двумя конкурентными исполнителями и сохранность данных после перезапуска (когда реализация будет создана).
