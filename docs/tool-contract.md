# Контракт Tool — сервис выполнения заданий (Qeu)

## 1. Назначение и границы

`Tool` — единый контракт обработчика операции внутри сервиса. `Dispatcher` выбирает зарегистрированный обработчик через `Registry` и вызывает его, не зная подробностей вычисления, преобразования текста или внешнего HTTP-запроса.

Контракт разработан для практики P2; реализация предполагается на следующих практиках. Он согласован с `docs/architecture.md` и публичным API `docs/api/openapi.yaml`.

`Tool` **не** создаёт `Job`, не меняет его состояние, не пишет в базу данных и не формирует HTTP-ответы. Этими задачами занимаются `JobService`, фоновый исполнитель, `JobRepository` и REST API соответственно.

## 2. Вход, выход и интерфейс

- **Вход:** `operation` — зарегистрированное имя операции; `params` — JSON-объект параметров, соответствующий схеме этой операции.
- **Успех:** `ToolResult` с `ok: true` и `output: { "value": ... }`, где значение — число, строка либо JSON-объект/массив.
- **Ошибка выполнения:** `ToolResult` с `ok: false` и `error: { "code": "...", "message": "..." }`; при наличии ошибочного поля добавляется `field`.
- **Взаимоисключение:** у успешного результата нет `error`, у неуспешного нет `output`.

Концептуальный интерфейс для будущей реализации на Python:

```python
from typing import Any, Mapping, Protocol


class Tool(Protocol):
    def validate(self, params: Mapping[str, Any]) -> None: ...
    # При некорректных параметрах: ToolInputError(code, message, field).

    def execute(self, params: Mapping[str, Any]) -> "ToolResult": ...
    # ToolResult: либо {ok: True, output: {value: ...}},
    # либо {ok: False, error: {code: ..., message: ..., field?: ...}}.
```

`ToolResult` здесь — **внутренний контракт**, а не JSON, который API напрямую отправляет клиенту. При успехе Worker сохраняет `output` в `Job.result` и переводит `running → done`; при ошибке сохраняет `error` в `Job.error` и переводит `running → failed`. `GET /jobs/{id}` возвращает объект `Job` из OpenAPI. Для существующей неуспешной задачи HTTP-статус GET остаётся `200`.

### Примеры `ToolResult`

Успех:

```json
{
  "ok": true,
  "output": { "value": 40 }
}
```

Ошибка выполнения:

```json
{
  "ok": false,
  "error": {
    "code": "PROVIDER_TIMEOUT",
    "message": "Внешний сервис не ответил в отведённое время"
  }
}
```

## 3. Регистрация, валидация и выполнение

1. `JobService` получает `operation` и `params` из `POST /jobs`; API проверяет JSON и типы данных по контракту OpenAPI.
2. `Registry` ищет обработчик по точному имени `operation`. Если операция неизвестна, API возвращает `400 UNKNOWN_OPERATION`, `field: operation`; **Job не создаётся**.
3. **До создания Job** вызывается `Tool.validate(params)`. Обработчик проверяет свои предметные ограничения (например, деление на ноль). При ошибке `ToolInputError` API возвращает `400 INVALID_PARAMS`, указывая `field`; **Job не создаётся**.
4. После успешной валидации `JobService` применяет правила `Idempotency-Key` из OpenAPI и сохраняет Job со статусом `created`. Новый Job возвращается с HTTP `202`.
5. Worker переводит Job из `created` в `running`, затем вызывает `Dispatcher`, а тот — `Tool.execute(params)`.
6. Worker сохраняет `output` либо `error` и завершает Job в `done` либо `failed`. Terminal states повторно не запускаются.

Таким образом, **проверка транспорта и общих типов** относится к API, **предметная валидация параметров** — к конкретному Tool (вызывается `JobService` до создания Job), **выбор Tool** — к Registry/Dispatcher, а **управление состоянием Job** — к доменной модели и Worker.

`Dispatcher` не содержит ветвлений по конкретным именам инструментов. Добавление Tool с прежним контрактом требует его регистрации и тестов, но не изменения кода Dispatcher.

## 4. CalculatorTool

**Операции:** `calculator.add`, `calculator.subtract`, `calculator.multiply`, `calculator.divide`.

**Параметры:** `{"a": number, "b": number}`. Оба поля обязательны; лишние поля недопустимы. `number` соответствует числовому типу JSON (без булевых значений).

**Проверка до создания Job:** отсутствие `a`/`b`, неверный тип либо `b = 0` для `calculator.divide` → `400 INVALID_PARAMS`, поле `params.a` или `params.b`.

**Результат:** `output.value` — число. Например:

```json
{
  "operation": "calculator.add",
  "params": { "a": 15, "b": 25 }
}
```

Результат Tool:

```json
{ "ok": true, "output": { "value": 40 } }
```

Математическая ошибка, не предусмотренная проверками, возвращает неуспешный `ToolResult` с понятным кодом `CALCULATION_FAILED`, без утечки деталей реализации.

## 5. TextTool

**Операции:** `text.uppercase`, `text.lowercase`.

**Параметры:** `{"text": string}`; текст обязателен, длина от 1 до 10 000 символов. Лишние поля недопустимы.

**Проверка до создания Job:** отсутствие поля, неверный тип, пустая строка либо превышение лимита → `400 INVALID_PARAMS`, `field: params.text`.

**Результат:** `output.value` — преобразованная строка. Например:

```json
{
  "operation": "text.uppercase",
  "params": { "text": "hello" }
}
```

Результат Tool:

```json
{ "ok": true, "output": { "value": "HELLO" } }
```

В рамках P2 регистр текста преобразуется стандартными правилами Unicode; язык не определяется отдельной ML-моделью.

## 6. HTTPTool и граница внешнего провайдера

**Операция:** `http.get`.

**Параметры:** `{"resource": string}`. `resource` — относительный идентификатор длиной 1–255 символов с символами `A–Z`, `a–z`, `0–9`, `/`, `_`, `-`. Произвольный URL клиент не передаёт; базовый адрес внешнего сервиса задаётся конфигурацией.

**Проверка до создания Job:** недопустимый `resource` → `400 INVALID_PARAMS`, `field: params.resource`.

**Исполнение:** `HTTPTool` делегирует сетевой вызов HTTP-адаптеру. Адаптер применяет ограниченный `timeout`, проверяет HTTP-статус и формат ответа. Успешный корректный ответ преобразуется во внутренний `output: {"value": ...}`; сырые поля провайдера не должны менять контракт `ToolResult`.

**Возможные ошибки выполнения:**

| `error.code` | Причина | Состояние Job после окончательной неудачи |
|---|---|---|
| `PROVIDER_TIMEOUT` | Время ожидания ответа истекло | `failed` |
| `PROVIDER_REQUEST_FAILED` | Провайдер вернул ошибку HTTP | `failed` |
| `PROVIDER_BAD_RESPONSE` | Формат ответа не соответствует ожидаемому | `failed` |
| `TOOL_EXECUTION_FAILED` | Другая контролируемая ошибка выполнения | `failed` |

Повторные попытки разрешаются **только при обоснованной безопасности повтора**. Потеря ответа не доказывает, что внешнее действие не произошло. Для операций с побочными эффектами без идемпотентности провайдера автоматический повтор запрещён; неопределённый результат фиксируется как ошибка выполнения, а факт возможного внешнего эффекта не скрывается. Детальная стратегия восстановления после аварийного завершения Worker — отдельное архитектурное решение и ограничение гарантий.

## 7. Соответствие внешнему API и ограничения

| Ситуация | Ответ REST API | Создаётся ли Job? |
|---|---|---|
| Неизвестное `operation` | `400`, `UNKNOWN_OPERATION`, `field: operation` | Нет |
| Некорректные параметры | `400`, `INVALID_PARAMS`, например `field: params.text` | Нет |
| Новый корректный запрос | `202`, объект Job (`created`) | Да |
| Тот же `Idempotency-Key` и те же данные | `200`, существующий Job | Нет новой Job |
| Тот же ключ с иными данными | `409`, `IDEMPOTENCY_KEY_REUSED` | Нет новой Job |
| Ошибка Tool после запуска | `GET /jobs/{id}` → `200`, Job (`failed`) с `error` | Да, существующая Job |
| Неизвестный `id` | `404`, `JOB_NOT_FOUND` | Нет |

Структура транспортных ошибок — `{"error": {"code": ..., "message": ..., "field"?: ...}}` (`ApiError`). Ошибка выполнения Tool сохраняется внутри Job в форме `ErrorDetail` без дополнительной оболочки `error`.

**Принцип OCP:** новая операция добавляется реализацией `Tool`, проверкой параметров, регистрацией в Registry и тестами. Dispatcher не меняется. Публичный OpenAPI-контракт обновляется, если новая операция становится доступной клиентам.

## 8. Проверяемые условия

- Неизвестная операция и ошибочные параметры отклоняются **до создания Job**.
- `CalculatorTool` выполняет четыре арифметические операции; деление на ноль отклоняется при валидации.
- `TextTool` выполняет преобразование регистра и проверяет ограничение длины.
- `Dispatcher` одинаково вызывает разные зарегистрированные Tool через общий контракт.
- Успешный `ToolResult` даёт `Job.status = done` и `Job.result`; ошибка выполнения даёт `Job.status = failed` и `Job.error`.
- Ошибка провайдера и таймаут не приводят к аварийному завершению приложения.
- Изменение формата внешнего провайдера требует изменений адаптера и его тестов, а не Dispatcher и контракта `ToolResult`.
