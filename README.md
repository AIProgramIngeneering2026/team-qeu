# Сервис выполнения заданий

## Описание проекта

Сервис предназначен для выполнения различных задач через единый API. Он решает проблему разрозненного запуска операций и отслеживания их выполнения.

Пользователь отправляет запрос, система создаёт задачу (Job), выбирает подходящий обработчик, выполняет операцию и сохраняет результат или информацию об ошибке.

## Пользователи

Разработчики и приложения, которым необходимо запускать вычислительные и текстовые задачи через API.

## Основные возможности

- Создание задач и получение их идентификаторов.
- Выполнение вычислений и обработка текста.
- Отслеживание состояния задач.
- Получение результатов и сообщений об ошибках.
- Сохранение истории выполнения задач.

## Границы проекта

**В систему входят:**
- API для управления задачами.
- Диспетчер и реестр обработчиков.
- Обработчики вычислительных и текстовых задач.
- Хранение задач и результатов.
- Обработка ошибок и интеграция с внешним HTTP-сервисом.

**В систему не входят:**
- Веб-интерфейс и мобильное приложение.
- Обучение собственных моделей машинного обучения с нуля.
- Облачное развёртывание.

## Дальнейшее развитие

В дальнейшем планируется интеграция LLM для обработки запросов на естественном языке и автоматического выбора подходящего обработчика.

## P3 — Доменное ядро (Python)

Ядро работает без HTTP-фреймворка и СУБД (они появятся в P4). Python 3.10+.

Реализованы модель `Job` с проверкой переходов, `Registry`, `Dispatcher`, `CalculatorTool` и `TextTool`, а также репозиторий в памяти.

Запуск тестов **одной командой из корня репозитория**:

```bash
python -m unittest discover -s tests -v
```

Поддерживаемые операции: `calculator.add`, `calculator.subtract`, `calculator.multiply`, `calculator.divide`, `text.uppercase`, `text.lowercase`.

Состояния: `created → running → done | failed`. Из конечных состояний возврата нет; недопустимые переходы вызывают `INVALID_STATE_TRANSITION`.

Валидация операции и параметров выполняется **до создания Job**.

Сценарий «перезапуск сервера» для З2 в P3 моделируется методом `InMemoryJobRepository.recover_after_restart()`: он переводит обнаруженные `running` в `failed` (`WORKER_INTERRUPTED`).

Реальной сохранности между процессами пока нет: в P4 нужна постоянная БД и механизм восстановления.

Отмена/удаление Job не поддерживаются; З3 неприменимо.
